# Проверка без настоящего роутера

Полной гарантии для GL-MT3000 программный стенд не даёт. Он проверяет определённые свойства скрипта в описанной модели, а не поведение всех аппаратных ревизий и прошивок.

## Как устроен стенд

1. GitHub Actions получает generic-ядро из официального репозитория Debian bookworm. SHA-256 пакета сверяется с HTTPS-индексом Packages. Это проверка целостности по тому же источнику; отдельной проверки подписи Debian Release в сборщике нет.
2. Создаётся отдельный initramfs с Python для управления тестами, статическим BusyBox и реальными модулями `nandsim`/`mtdblock` этого ядра.
3. QEMU загружает эту систему без сети, дисков и доступа к файловой системе хоста. При наличии KVM используется ускорение, иначе TCG.
4. Linux nandsim предоставляет виртуальный NAND с разделом 2 MiB и блоком стирания 128 KiB. Это пример геометрии, не воспроизведение конкретного чипа Beryl.
5. Внутри гостя создаётся chroot с данными модели Beryl и меткой Factory. Системный скрипт **копируется побайтно без изменений**. Запускаются его настоящий `main`, проверки, `dd`, `sync`, `od`, `awk`, резервное копирование и диалоги через PTY.
6. Скрипт пишет через реальный Linux mtdblock. Стенд проверяет весь результат через символьный `/dev/mtdN`, отдельно от кеша чтения mtdblock. Ожидается отличие только двух байтов.

Сам файл скрипта и его SHA-256 в этом испытании не меняются. Режима обхода проверок в клиентский скрипт не добавлено.

## Что является имитацией

- Идентификатор модели, строка версии GL.iNet и метка Factory в таблице MTD — явно созданные фикстуры.
- Содержимое Factory синтетическое: маркеры, CN и известный фон. Дамп настоящего устройства не использован.
- Статический BusyBox имеет архитектуру x86-64. Это не BusyBox из конкретной прошивки GL.iNet.
- Ядро и драйверы Debian отличаются от сборки GL.iNet и драйвера контроллера MT7981.
- Сброс настроек отложен, а `reboot`/`poweroff` недоступны внутри chroot. Работа настоящего `firstboot`, загрузчика, VPN и Wi-Fi не проверяется.

## Какие сценарии проверяются

Для каждого префикса `00 CN` и `FF CN`: проверка без записи; отмена до копии; отмена после создания проверенной копии; смена CN → US с полным сравнением NAND и сохранением исходной копии; повторный запуск без CN с отказом от записи.

Отдельно: несколько сигнатур страны, неизвестная структура Factory, другая модель, неоднозначная таблица Factory. Итого 14 сценариев. Они дополняют 19 обычных автотестов, а не заменяют их.

Результаты каждого запуска доступны в [NAND integration](https://github.com/illegalFeed/GL.iNet-Region-Changer/actions/workflows/nand.yml). Успешным результатом считается прохождение всех утверждений, вывод `BERYL_NAND_SUITE_SUCCESS` и успешное завершение шага. Ошибки подготовки стенда или тайм-аут не считаются прохождением проверки скрипта.

## Как повторить

В одноразовой Linux VM с root-доступом, QEMU, BusyBox static, Python 3, kmod, cpio и dpkg-deb:

```sh
sudo python3 tests/build_nand_vm.py
sudo python3 tests/run_nand_vm.py
```

Скрипт `nand_integration.py` загружает модули только при специальном флаге и отказывается запускаться при наличии ранее созданных MTD. Его штатный способ запуска — внутри создаваемой QEMU VM; не запускайте его на роутере.

## Почему не просто загрузить прошивку Beryl в QEMU

QEMU требует модель конкретной платы. В исследованном списке поддерживаемых ARM-плат модели GL-MT3000/MT7981 не обнаружено; одного ARM-процессора или универсальной платы `virt` недостаточно для запуска штатного ядра. Документация QEMU прямо описывает эту границу. Это вывод по проверенному набору QEMU, а не утверждение об отсутствии любых сторонних исследовательских эмуляторов.

Чтобы проверить весь путь «Factory → чтение региона при загрузке → интерфейс GL.iNet», нужны точная прошивка, её механизмы чтения региона и достоверная модель аппаратной части. Этот стенд такой путь не эмулирует. Даже при его успешном прохождении версия остаётся RC; отсутствие настоящего устройства не превращает эмуляцию в аппаратную сертификацию.
