# Для владельца репозитория

## Обновление публикации

Репозиторий: [illegalFeed/GL.iNet-Region-Changer](https://github.com/illegalFeed/GL.iNet-Region-Changer), публичная ветка `main`.

1. Перед обновлением выполните локальные тесты и проверьте изменения.
2. SHA-256 в команде README и в SHA256SUMS должен совпадать с байтами `beryl-region.sh`. После изменения скрипта пересчитайте его: `sha256sum beryl-region.sh`.
3. Публикуйте скрипт, контрольную сумму и инструкцию одним коммитом. Дождитесь успешных проверок в Actions.
4. Не рассылайте RC клиентам до проверки ниже. После реального испытания запишите модель, версию штатной прошивки, board_name и результат в TEST_REPORT.md. Для релиза измените версию, обновите контрольную сумму в документах и повторите тесты.

## Проверка на собственном Beryl AX

Сначала сохраните настройки, подготовьте стабильное питание и компьютер с SSH/SCP. Заводская копия содержит индивидуальные данные устройства; не загружайте её в репозиторий, Issues или публичный чат.

- На новом CN-устройстве выполните `sh beryl-region.sh --check`, зафиксируйте модель и версию. Если скрипт остановился — не обходите проверки, изучите причину.
- Запустите мастер, проверьте копирование `factory-original.img` на компьютер. Проверьте два пути отмены: до копии и после копии. До `SAVED` Factory не должен меняться.
- Выполните смену региона, убедитесь в успешном полном сравнении Factory. Сначала можно отложить сброс, затем выполнить его в панели; либо явно подтвердить `RESET` в мастере.
- Настройте устройство заново. Проверьте интернет, доступность VPN-разделов и AdGuard Home, Wi-Fi и повторную загрузку. Наличие всех функций зависит от состава штатной прошивки; смена кода не устанавливает отсутствующие компоненты.
- Повторный запуск после смены должен остановиться без записи, поскольку CN больше не найден. Скрипт не определяет актуальный регион по фиксированному документированному полю, поэтому отсутствие CN не объявляется доказательством успешной разблокировки.

## Технические границы

Пишутся только два байта в `/dev/mtdblockN`, как в исходном подходе. Драйвер MTD может физически перезаписать блок флеш-памяти; прерывание питания остаётся риском. Сравнение выполняется через тот же интерфейс mtdblock после `sync`, не через независимый программатор. Автоматического восстановления Factory нет: ошибочная попытка восстановления может ухудшить ситуацию. При ошибке после начала записи мастер просит не сбрасывать и не перезагружать устройство.

Проверка модели использует точные имена `glinet,gl-mt3000`, `glinet,mt3000-snand`, `gl-mt3000`, наличие `/etc/glversion` и однозначный MTD label Factory. Это консервативный фильтр, не исчерпывающая сертификация всех аппаратных ревизий. `firsttest` и `secondtest` взяты из исходного проекта, точное поле региона производителем не документировано в используемых источниках. Скрипт не меняет настройки радиочастот Wi-Fi, не прошивает глобальную прошивку и не гарантирует доступность каждого компонента на любой версии.

Для разбора обращения достаточно текста ошибки, модели и версии прошивки. Не просите клиента публиковать пароли или полный Factory. Резервная копия предназначена только для того устройства, с которого снята.

## Локальные тесты

```sh
sh -n beryl-region.sh
python3 -m unittest discover -s tests -v
TEST_SHELL='busybox ash' python3 -m unittest discover -s tests -v
shellcheck -s sh beryl-region.sh
```

Тесты используют обычные файлы и подмену аппаратных путей в изолированной копии функций. Рабочий скрипт не содержит режима обхода аппаратных проверок. Автотесты не моделируют реальную флеш-память, загрузчик или работу VPN после сброса.
